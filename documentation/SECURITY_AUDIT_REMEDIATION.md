# Security audit remediation

Source: the supplied Tomeva v1.0.7 audit, checked against `bc0ff87`. Changes below are local source changes. Firebase rules, hosting, and released installers have not been deployed.

## Findings, one by one

| Audit item | Local result | Deployment or practical limit |
| --- | --- | --- |
| 1. Unverified student impersonation | Student profile writes/deletes, authorization removal, request creation and cancellation require a verified email. Regression tests attempt impersonation with an unverified token. | Publish the new rules in the institution's Firebase project. |
| 2. Unguarded Electron IPC | Sensitive Librarian handlers verify the exact local main frame and an unlocked workstation. Dialog operations recheck after awaiting user selection. Unused generic dialogs and renderer log writing were removed. Admin and Control Center frame checks were tightened too. | Rebuild/install desktop applications. |
| 3. Anonymous student PII reads | Students can get only their own verified profile/access document. Staff and approved kiosks retain the collection access needed for administration and roster sync. | Admission reservations replace portal collection enumeration; migrate existing records before rollout. |
| 4. Weak PIN | New PINs require 6–12 digits. The verifier is encrypted with secure OS storage, including automatic protection of legacy hashes when that storage is available. Failed-attempt counters/cooldowns persist in SQLite. Linux `basic_text` storage is rejected for PIN setup and kiosk secrets. | Existing four-digit PINs should be changed. The screen lock does not encrypt SQLite or replace OS account/disk protection. Secure OS storage must be available. |
| 5. Firestore document size | Public and private snapshots use bounded pages plus a small generation manifest. The writer limits document and batch size, stages pages before publishing, and retires its old public/private generations after 24 hours. Readers support both legacy snapshots and the new format. A 10,000-book Unicode test verifies reconstruction and bounds. | Deploy new readers before enabling the new writer. Spark storage/read/write quotas still apply. Cleanup metadata belongs to each workstation; loss of its SQLite settings may require operator cleanup of orphaned generations. |
| 6. Missing shape/size limits and spoofed request identity | Manifests/pages, notification documents, control flags and requests have bounded shapes. Student requests must use the admission number and name approved in their own authorization record. Profile admission ownership is checked atomically. | Legacy authorization records need admission numbers filled by migration. Array pages are bounded; individual row contents come from the validated desktop writer. |
| 7. Public catalog quota abuse | Complete public generations are cached in memory and, where space permits, local storage for repeat visits. Private circulation is never persisted in that cache. | **Mitigated, not eliminated.** Public Firestore reads still let a determined client consume quota. Client caching cannot enforce a server read rate. A hosting/cache or attestation design covering both web and Electron clients needs institution infrastructure decisions; do not enable Firestore App Check enforcement before desktop compatibility is provided. |
| 8. All staff can administer kiosks | Staff authority requires an explicit active `staff_accounts` grant. Kiosk provisioning/revocation and update approvals additionally require an enabled `kiosk_admins` grant for the user's UID and library. The UI checks these grants too. | Create grants through Firebase Console with an institution operator account. Client apps cannot grant themselves authority. |
| 9. Dead Cloud Function | Removed `functions/mintKioskToken.js`, the unused Functions SDK script, and its obsolete test. | No Cloud Functions are required. Historical `kiosk_registry` client access remains denied. |
| 10. CSP and CDN dependency | Removed inline script execution and event attributes from Librarian, Admin and Student pages. Handlers are compiled listeners; Firebase web code is bundled from the locked local SDK. Admin navigation is blocked. | `node scripts/prepare-client.cjs` prepares web bundles. CSS inline styles remain allowed. Real Google sign-in still requires network access and its trusted Google iframe/script origins. |
| 11. Unverified backups | Main generates backups from SQLite. Versioned JSON includes a SHA-256 checksum. Restore checks row shapes, identifiers, active-loan consistency, payment references and settings; shows counts; and checkpoints SQLite before replacing data. Legacy JSON needs explicit confirmation. | JSON backups are portable **plaintext**. A checksum detects corruption, not authenticity against someone who can rewrite the whole file. Protect backups with secure storage; OS-protected PIN/credential material is excluded. |
| 12. File-controlled book status | Catalog imports preserve existing statuses, force active loans to `Issued`, and initialize new catalog entries as `Available`. Imported status fields cannot make lost/damaged books available. Invalid direct status values are rejected. | Use circulation/damage operations to change status deliberately. |
| 13. Update trust chain | Detached Ed25519 signatures authenticate `SHA256SUMS`; installers are hashed against that signed manifest and rechecked before launch/install. All desktop update paths enforce package checksums and require signatures when publisher keys are configured. Release-build configuration supports an existing Windows certificate and requires signing configuration when `TOMEVA_REQUIRE_SIGNING=1`. | **Publisher setup pending.** No production signing key was generated. `release-keys.cjs` intentionally contains no trusted key. By publisher decision, unsigned development/pilot releases remain allowed while the embedded key list is empty. These verify GitHub HTTPS checksums without publisher authenticity. Once a key is configured, missing/invalid signatures fail closed with no unsigned fallback. Windows certificates also need to be supplied by the publisher. |
| 14. Linux installer launch | Control Center rechecks the package hash immediately before launching the selected installer. | Publisher authenticity requires configured signing; unsigned pilots use HTTPS checksums as described in item 13. |
| 15. Log forgery, flooding and integrity | Renderer append access was removed. Internal lines are bounded and sanitized; log exports are rate limited. Each record has an OS-key-protected HMAC chain. A SQLite outbox commits with the business change and replays after failures/restarts; record IDs prevent duplicate replay. Verification checks for missing exported events too. | Old `.log` files are historical unsigned records. New `.audit.log` files are signed. Loss of OS key access defers export while events stay in SQLite; tampering with both the entire database and its local history is outside the screen-lock guarantee. |

## Changes to the referenced remediation pack

- **P0-01:** catalog and legacy-root writes require staff or an approved kiosk. Authentication now precedes every outbound snapshot; offline/unprovisioned sync is deferred and local desk operations continue.
- **P0-02:** students no longer enumerate login/access collections. `adm_claims/{encoded-admission-key}` and a login profile are written in one batch; another account cannot overwrite the reservation. Staff administration/imports reserve admission numbers too.
- **P0-03:** an explicit staff grant prevents students sharing the staff domain from gaining staff authority. Administrator grants separate provisioning/update authority from ordinary staff.
- **P1-01/P1-03:** existing SQLite transaction wrappers were retained. Fault tests cover rollback; undo history now persists in SQLite; logging uses the durable outbox; arbitrary renderer-supplied undo action objects were removed.
- **P2-03:** runtime dependency audits were run for all three desktop applications. Each reported zero vulnerabilities. The Student Portal now uses the local locked Firebase SDK bundle.
- **P3/P4/P8:** existing approved-tag pinning, downgrade prevention, pre-install backups, encrypted Control Center recovery and recovery tests were retained. Publisher signature verification and restore validation close the concrete additional gaps identified by this audit.
- **P7-02:** `.github/workflows/security.yml` runs application tests, runtime dependency audits for every app, Firestore emulator tests and Windows builds on pushes/PRs.

Admission keys normalize case and escape percent signs and slashes so existing admission formats are preserved. The rule and JavaScript normalization use the documented [Firebase string operations](https://firebase.google.com/docs/reference/rules/rules.String#replace).

## Institution rollout

1. Back up existing Firebase data and local SQLite data. Resolve duplicate/mismatched admission records while registrations are paused.
2. With existing operator credentials, run `node scripts/migrate-security-data.cjs --project=PROJECT_ID` to inspect the admission migration. It is a dry run by default. To apply, add `--apply --backup=ABSOLUTE_PATH_OUTSIDE_REPOSITORY`. The script refuses conflicts and saves a private snapshot before writing. It does not create staff/admin grants.
3. In Firebase Console, create `staff_accounts/{lowercase-email}` with `{ active: true }` for approved staff. For each kiosk/update administrator, create `kiosk_admins/{Firebase-Auth-UID}` with `{ enabled: true, libraryId: "main" }`. Only grant actual staff, including when students share their domain.
4. Build the web clients with `node scripts/prepare-client.cjs`. Deploy the new Student Portal and Admin client together with the generated institution rules/indexes. Use Control Center's regenerated rules, which substitute the institution domain. The canonical rules, template rules and `firestore.txt` are kept in sync.
5. Configure an **existing** public Ed25519 key with `node scripts/configure-release-key.cjs PATH_TO_PUBLIC_KEY`. Its matching private key stays outside the repository. Supply an existing Windows certificate through the builder's certificate environment and `TOMEVA_WINDOWS_PUBLISHER`; set `TOMEVA_REQUIRE_SIGNING=1` for signed release builds. Sign the final manifest with `node scripts/sign-release.cjs PATH_TO_SHA256SUMS PATH_TO_EXISTING_PRIVATE_KEY` and publish the resulting `SHA256SUMS.sig` with the release assets. Rebuild all desktop clients to embed the trusted public key.
6. Install the new desktop clients, activate the kiosk, replace legacy four-digit PINs, then sync. Check student registration/request ownership, staff access, revocation, a complete sharded catalog, backup restore and signed log verification.

## Verification

- Full local application test suite, SQLite rollback/persistence tests, security tests and Firestore emulator tests.
- Electron smoke checks for Librarian offline issue/return, PIN lock/unlock, Admin sandbox/setup, and Control Center rules/export/recovery. Signed package fixtures used only in test memory; the production trust configuration stayed empty.
- Runtime dependency audits for Librarian, Admin and Control Center.
- CI configuration was added locally; a hosted GitHub Actions run has not been observed.

Publisher signing is intentionally deferred for the unsigned 1.0.8 pilot. A complete defense against abuse of public Firestore reads also remains external. Institution deployments require coordinated rollout above.

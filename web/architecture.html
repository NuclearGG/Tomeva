Where every library

Four applications, one institution-owned system. Circulation begins at the local desk; Firebase connects administrators and readers.

OPERATING RULE

One authoritative circulation desk per library. Admin and the portal can serve many devices. Independent Librarian databases do not merge.

01

LIBRARIAN / ELECTRON

A local ledger, with controlled cloud access.

Daily circulation stays on the workstation. A PIN unlocks the desk; a library-bound kiosk account enables protected synchronization.

  1. 01 / INTERACTIONSandboxed renderer

    Books, borrowers, loans and returns.

  2. 02 / TRUST BOUNDARYPreload → allowed IPC

    Trusted frame, unlock checks and bounded inputs.

  3. 03 / BUSINESS RULESLibrary service

    Transactional changes and relationship validation.

  4. 04 / PERSISTENCESQLite + durable outbox

    WAL, schema migrations, FTS5 and local audit.

Circulation integrity

  • Accession identifiers use canonical case matching.
  • One active loan per copy. Imports preserve active loans and borrowers.
  • Damage handling closes an active loan before changing availability.
  • App-level relationship checks preserve archived history; the JSON record tables do not use relational foreign keys.

Snapshot synchronization

  • Public catalog_shards stay separate from protected circulation_shards.
  • Stages shards before publishing the manifest; batches are sent sequentially.
  • Kiosk credentials are protected by the operating system and scoped to the project and workstation.
  • Snapshot publication is last-writer-wins; it cannot reconcile two independent desks.

02

ADMIN / ELECTRON

Every privileged change has an owner.

ACCESS CHAIN

Verified Google sign-in → Configured staff domain → Enabled staff grant

Library administration additionally requires an enabled UID-based administrator grant.

Authority comes from records

staff_accounts/{email} grants staff access. kiosk_admins/{uid} binds a library administrator to the library. A matching email domain alone does not grant administrative access.

Administrators manage admission rosters, student access, kiosk provisioning and update approvals. They read synchronized circulation; they do not write directly to the desk’s SQLite database.

Writes leave a recoverable trail

A protected mutation writes the target, an immutable admin_audit event and its audit head in one transaction. Actor, time and before/after values are recorded.

Recovery checks the current record and admission claim before restoring a deletion. It cannot overwrite a newer record or take another student’s claim.

BOUNDED READING

25 records at a time

Directory queries use server cursors. Snapshot browsing caches at most four shards in memory; the cache clears when the viewer closes or the user signs out.

03

STUDENT PORTAL / INSTITUTION-HOSTED WEBSITE

A request is a workflow, not a loan.

Readers browse the catalogue and submit their own requests. The desk makes circulation decisions. Private circulation snapshots are not exposed to portal accounts.

Identity and limits

Firebase Google sign-in, student authorization or an explicit staff grant, and a 10-hour portal session. Each UID can submit 100 book requests per 10-hour window.

The request and quota increment are atomic and enforced by Firestore rules. This limits request submissions, not all site visits or catalogue reads.

Account removal

The student requests deletion. Authorized staff remove the protected student access/profile records and mark completion; the student can then delete their own Firebase Auth account.

Circulation history and retained archives follow the institution’s retention policy.

04

CONTROL CENTER / ELECTRON

Set up once. Keep the institution in control.

  1. 01 / CONFIGUREInstitution settings

    Firebase project, staff domain and portal URL.

  2. 02 / VERIFY & EXPORTGitHub Release packages

    Download, check SHA-256 and size, then generate configured handoff folders.

  3. 03 / DEPLOYApps, rules and portal

    Install desktop apps and publish matching Firebase rules and the institution site.

Live appearance, without new packages

Authorized administrators publish revisioned settings to libraries/main/public/appearance. Connected apps listen for changes and retain the last settings for offline use.

Deliberate updates

Control Center downloads separate applications; they are not embedded in its installer. Its own stable updates require an operator action, verification and a recovery checkpoint.

Admin and Librarian updates also follow the institution’s approval policy. A project or domain switch clears the previous institution’s session scope.

05

RECOVERY / TWO SEPARATE RESPONSIBILITIES

Bring back the setup. Then the ledger.

INSTITUTION CONFIGURATION

Encrypted Recovery Kit

Restores the setup configuration used by Control Center. Keep the Kit password separately from the Kit.

Does not contain circulation records.
CIRCULATION DATA

Librarian backup + checkpoint

Checksummed exports validate the active loan graph before restore. Native SQLite checkpoints support rollback and migration recovery.

Store circulation backups apart from Kits.

For a desk transfer, stop writes on the old desk, restore and verify the new desk, then activate its kiosk credentials. Operating-system-bound credentials require reactivation on another computer.

06

DEPLOYMENT / READ BEFORE ROLLOUT

What this architecture assumes.

Institution ownership
Each institution owns its Firebase project, account grants, data and portal hosting. The public Tomeva project site is separate from the Student Portal.
Matching rules and clients
Generated rules need explicit deployment. This page describes the v1.0.10 source; it does not certify the rules currently deployed in an institution’s Firebase project.
Unsigned pilot releases
Release signing is intentionally deferred. SHA-256 detects changed downloads against the manifest; it does not independently authenticate the publisher. Existing trust-key support allows future signature enforcement.
Scale and compatibility
Pagination and FTS bound browsing work. Snapshot construction still uses memory for the full data set. Legacy Windows builds use the unsupported Electron 22 runtime.
